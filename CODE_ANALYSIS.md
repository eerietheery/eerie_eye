### Eerie Eye Project Analysis

#### 1. Overall Architecture and Workflow

The application is a graphical image manipulation tool built with Python's **Tkinter** library for the UI and **Pillow (PIL)** for image processing. Its architecture is modular, separating UI, effects, and core application logic into different directories.

-   **Entry Point (`main.py`):** The application starts here. It sets up logging and initializes the main Tkinter window and the `EerieEye` class.
-   **Main Application (`eerie_eye.py`):** The `EerieEye` class is the central coordinator. It builds the main UI by assembling components from the `ui` directory, manages the application state (loading/saving images, undo stack), and orchestrates the application of effects.
-   **UI Components (`ui/`):**
    -   `ImageCanvas`: Displays the main image.
    -   `WaveformCanvas`: Shows RGB channel waveforms of the image and allows the user to select regions to apply effects to.
    -   `EffectFrame`: A crucial UI panel that contains a dropdown to select an effect and dynamically generates parameter controls (sliders, checkboxes) for the chosen effect.
-   **Effects Logic (`effects/`):**
    -   `EffectManager`: A static class that acts as a registry for all available image effects. It maps effect names (strings) to their corresponding processing functions.
    -   **Individual Effect Files** (e.g., `pixel_sort.py`, `wave_distortion.py`): Each file contains a pure function that takes a PIL Image, a dictionary of parameters, and optional selections, and returns a new, modified image as a NumPy array or PIL Image.

The general workflow is as follows:
1.  The user opens an image via the "Open Image" button.
2.  The image is loaded into `EerieEye`, and a preview is displayed in `ImageCanvas`, with its waveform shown in `WaveformCanvas`.
3.  The user selects an effect from the dropdown in `EffectFrame`.
4.  `EffectFrame` dynamically creates the UI controls (sliders, etc.) for that effect's parameters.
5.  The user adjusts the parameters. With each adjustment, a real-time preview is generated by calling `apply_glitch_realtime`.
6.  The user can also select specific regions on the `WaveformCanvas` to limit where the effect is applied.
7.  When satisfied, the user clicks "Apply Glitch". This commits the currently selected effect and its parameters to an `applied_effects` list. The entire stack of committed effects is then re-applied to the original image to produce the new "current" image.
8.  The "Undo" button removes the last committed effect from the stack and re-applies the remaining ones.

#### 2. GUI Parameter Handling

This is a key part of the application's design and works as follows:

1.  **Control Creation:** When an effect is selected in the `EffectFrame` dropdown, the `update_effect_params` method is triggered. It consults a hardcoded dictionary to determine which parameters are needed for the selected effect (e.g., `pixel_sort` needs `threshold`, `sorting_function`, `direction`).
2.  **Dynamic UI Generation:** Based on the parameter names, helper methods like `create_pixel_sort_params` dynamically instantiate Tkinter widgets (`ttk.Scale`, `ttk.Combobox`, `tk.Checkbutton`). Each widget is configured with a default value, range, and a callback function.
3.  **Real-time Updates (Preview):** The most important callback is `on_slider_change`. This method is bound to any change in the sliders or comboboxes. It uses a debouncing mechanism (a 30ms timer) to prevent too many updates while a slider is being dragged. After the delay, it calls the `apply_glitch_realtime` method passed down from `EerieEye`.
4.  **Parameter Collection:** When it's time to apply an effect (either for a preview or a final commit), the `EffectFrame.get_effect_params()` method is called. It iterates through all the dynamically created UI widgets in its `param_entries` dictionary and calls their `.get()` method to retrieve the current value.
5.  **Type Conversion:** Inside `get_effect_params`, there is logic to convert the string/float values from the widgets into the correct data type (e.g., `int` for a threshold, `float` for a decay factor, `bool` for a checkbox).
6.  **Passing to Effect:** This dictionary of parameters is then passed directly to the corresponding effect function (e.g., `pixel_sort(...)`) via the `EffectManager`.

This system allows for adding new effects and their corresponding UI controls in a relatively decoupled manner, although it requires adding new UI creation logic to `EffectFrame` for each new effect.

### Bug Fixes and Improvements (July 22, 2025)

#### **Fix 1: UI Freezing and Performance**

-   **Background Processing:** The primary bug causing the UI to freeze during image processing has been resolved. All effect applications are now offloaded from the main UI thread to a background thread pool (`ThreadPoolExecutor`).
-   **Asynchronous UI Updates:** A `queue.Queue` system was implemented. The background thread places processed images into the queue, and a periodic checker on the main thread safely retrieves these results and updates the image canvas without blocking the UI.
-   **Efficient Undo Operation:** The `undo` functionality was significantly optimized. Instead of re-calculating the entire effect stack, it now instantly restores the previous image state from the `undo_stack`, making the operation much faster and more responsive.
-   **Graceful Shutdown:** The application now properly shuts down the background thread pool when the main window is closed, preventing lingering processes.

#### **Fix 2 & 3: Code Structure and Efficiency**

-   **Modularization:** The core application logic (state management, effect processing, caching) was extracted from `eerie_eye.py` into a new, dedicated `app_logic.py` file. This greatly improves the separation of concerns, making `eerie_eye.py` a pure UI controller.
-   **Efficient Effect Caching:** An intelligent caching system was implemented in `app_logic.py`. It stores intermediate image results after each effect is applied. When processing, it finds the most recent cached state and only computes the necessary changes, dramatically improving performance for long effect chains.
-   **Code Consolidation:** The redundant `ui/effect_params.py` file was deleted, and its logic was consolidated into `ui/effect_frame.py`. This removes duplicate code and simplifies future maintenance.

#### **Fix 4 & 5: Error Handling and Plugin Architecture**

-   **Robust Error Handling:** The asynchronous processing queue was built to properly handle exceptions from the effect processing thread. Errors are now caught, logged, and displayed in a `messagebox` to the user without crashing the application.
-   **Dynamic "Plugin" Architecture:** The hardcoded UI generation has been completely removed. A metadata-driven system is now in place:
    -   Each effect file in the `effects/` directory now defines its own parameters using a standardized `PARAMS_META` list.
    -   The `EffectManager` automatically discovers these effects and their metadata.
    -   The `EffectFrame` is now a generic UI builder that reads the metadata and dynamically generates the appropriate sliders, dropdowns, and checkboxes for any given effect.
-   **Scalability:** This new architecture is highly scalable. Adding a new effect is as simple as adding a new Python file to the `effects` directory with the required function and metadata, with no further changes needed to the UI code.
